## Feature 2: Dynamic Schema for Categories
### 1. Executive Summary
 * **Title:** Category-Specific Metadata Templates & Validation
 * **Summary:** This feature allows the manual entry portal to adapt its interface based on the selected category. By defining "schemas" for different types of logs, the system ensures that relevant data is captured consistently (e.g., a "Workout" log prompts for duration, while a "Recipe" log prompts for ingredients).
### 2. Context & Objectives
 * **Background:** A generic text box is often insufficient for structured data. Without guidance, users often forget to record key metrics, making the logs less useful for future analysis or filtering.
 * **Goals:** * Provide a tailored entry experience for different areas of life.
   * Ensure data consistency across logs within the same subcategory.
 * **Non-Goals:** This is not a full database management system; it is a flexible UI layer that sits on top of Markdown frontmatter.
### 3. Proposed Solution
#### High-Level Architecture
The system will maintain a schemas.json configuration file. When a user selects a directory/category, the portal lookups the corresponding template and renders the appropriate input fields.
#### Detailed Design
 * **Schema Definition:** Each category can define custom fields (e.g., number, select, date, checkbox).
 * **Frontmatter Injection:** Values entered into these custom fields are automatically mapped to the YAML frontmatter of the Markdown file.
 * **Default Fallback:** If no schema is defined for a subcategory, the system falls back to a "Standard Log" template (Title + Body).
### 4. Alternatives Considered
 * **Hard-Coded Forms:** Dismissed because it prevents the user from creating new, custom categories on the fly.
 * **Post-Processing Scripts:** Dismissed because it's better to capture structured data at the source than to try and parse it out of raw text later.
### 5. Execution Plan
 * **Phase 1:** Create the JSON schema engine that can render dynamic form inputs.
 * **Phase 2:** Update the file-saver logic to merge these dynamic inputs into the YAML header.
 * **Phase 3:** Build a simple "Template Creator" UI so the user can define new schemas without editing JSON files directly.
### 6. Risks & Mitigations
 * **Risk:** Changing a schema might make older logs "invalid."
 * **Mitigation:** The system will treat schemas as "suggested fields" rather than "strict requirements" for historical entries, preventing errors when viewing older logs.
